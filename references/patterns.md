# Skill 写作模式与 token 预算

## description 配方

公式：`做什么` + `什么时候用（用户会说的话 / 场景）` + `关键词`。

好：

- `从 PDF 提取文本和表格。当用户给出 PDF 并要求提取、转换或分析内容时使用；提到发票、扫描件、报表也算。`

坏：

- `PDF 处理技能。`（没有触发场景）
- `本技能用于帮助用户处理 PDF 文件，提供多种能力……`（介绍口吻，浪费字符）

检查：遮住正文，只看 description，能否做对「用 / 不用」的判断？

## 三层加载

```
metadata  ～100 词        永远付费
body      触发时整份付费
resources 按需付费
```

设计动作：

- 高频步骤 → 正文
- 低频长文 → `references/`
- 确定性计算 → 脚本（执行不读入）
- 大示例 → `examples/`

## Token 预算表

| 部分 | 目标 | 硬上限 |
|---|---|---|
| description | ≤350 字 | 1024 字符 |
| SKILL.md 正文 | ≤200 行 / ≤3000 字 | 500 行 |
| 单个 reference | ≤300 行 | 无（超 300 行加目录） |
| 脚本 | 单文件可运行 | 无 |

## 模式

### 1. 选择器 + 分文件

一个 skill 支持多平台 / 多格式时，正文只做选择，细节放 `references/aws.md`、`references/gcp.md`，只读命中的那份。

### 2. 脚本优先

重复的格式转换、校验、计数，写成脚本；正文只写「何时运行、参数、失败怎么办」。

### 3. 模板外置

输出格式固定时，把模板放 `assets/`，正文说「以模板为准」，不要贴全文。

### 4. 反例驱动

正文里放 1 个「坏例子 → 为什么坏 → 怎么改」，比 5 条抽象规则更省 token。

## 反模式

- 把官方规范整段抄进正文
- 同一规则在 description、正文、reference 各写一遍
- `references/` 放了 8 个文件，正文一个都没提
- 为 3 行规则建一个 skill
- description 只有领域名（`Blender 技能`）
- 正文用大量 `MUST / NEVER` 代替解释
- 示例是占位符（`foo`、`bar`），学不到东西

## 重构清单（先删后加）

1. 删：不改变行为的句子、重复规则、没人读的文件。
2. 移：长示例 → `examples/`；查表 → `references/`；重复计算 → `scripts/`。
3. 并：同一主题的 references 合并成一个。
4. 改：description 补触发词；正文补「何时读哪个资源」。
5. 测：校验器 0 error；负例会红；触发词覆盖真实说法。
